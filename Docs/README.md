## 8차: 관찰 개수 표시·모래주머니로 지킨 보조 통로 (2026-11-09, 브랜치 `feature/field-polish`)

### 1. 관찰 개수
- **원인**: HUD의 '관찰 n/m'이 필수 관찰 대상(`mustObserve`)만 셌습니다. 현장 1은 필수 A·B·C에 추가 D, 현장 2는 H·W에 추가 O, 현장 3은 P·R에 추가 B라서 3·2·2로 보였습니다. 수첩 관찰 카드도 관찰 전 추가 대상은 빼고 보여 줬고, 다음 현장 소개의 '살펴볼 곳'도 필수만 셌습니다.
- **수정**: 전체 관찰 진행도와 승인 조건을 나눴습니다(`FieldRules.ObservableCount`·`ObservedCount`·`RequiredObservationCount`, 미션 데이터에서 계산).
  - HUD: 큰 줄 '관찰 0/4'(추가 포함 전체), 작은 줄 '필수 0/3' → 다 보면 '필수 관찰 완료'.
  - 수첩: '현장 확인 기록 n/전체', 관찰 전 추가 대상도 '추가 · 아직 못 봄' 카드로 보이며 종류·단서는 숨깁니다. 승인 불가 이유는 '필수 관찰이 n곳 남았어요', AI 단서 안내는 '필수 관찰 뒤 볼 수 있어요'.
  - HUD 문제 이름: 관찰 전이면 추가 대상에도 '?' 표시.
  - 다음 현장 소개: '살펴볼 곳 n곳 · 필수 m곳', 추가 칸에 '추가' 표시.
  - 승인 조건(`CanConfirm`의 필수 관찰)은 그대로라 추가 대상을 보지 않아도 승인할 수 있습니다. 같은 대상 재관찰·다른 현장 ID는 세지 않습니다. 저장·이어하기·재계획·재도전의 관찰 기록 정책은 바꾸지 않았고, 표시는 그 기록에서 계산합니다.
- 결과: 현장 1 0/4 → 4/4(필수 3), 현장 2 0/3 → 3/3(필수 2), 현장 3 0/3 → 3/3(필수 2).

### 2. 모래주머니로 지킨 보조 통로(현장 3)
- **확인**: 판정은 정상이었습니다(보조 통로 입구 + 모래주머니 → B 해결, 현장 그림도 같은 확정 결과 `FieldEvaluation`과 같은 문제 ID B를 씀). 원인은 그림의 물높이였습니다. `FieldWorld.Water`가 모래주머니로 해결한 곳을 대응이 끝난 뒤에도 처음의 얕은 물(0.12)로 고정해, 옅은 물 막이 남아 미해결처럼 보였습니다.
- **수정**: 모래주머니로 해결한 곳의 물높이 = 처음 얕은 물 × (1 − 시설 대응).
  - 계획 단계·설치 직후·강우 중(대응 전): 처음의 얕은 물 그대로(해결 모습을 미리 보이지 않음, 강우에도 더 오르지 않아 깊은 물·표지·막힘 없음).
  - 대응 완료: 막힌 안쪽 통로의 얕은 물이 사라지고 옅은 젖은 바닥 자국만 남음. 물결·깊은 물·주의 표지·충돌 모두 없음. 펌프처럼 빨아들이는 연출은 없고 색만 옅어집니다.
  - 그림·물결·깊은 물·표지·충돌은 모두 이 물높이 하나를 따르므로 서로 어긋나지 않습니다. 정문(R) 등 다른 구역은 각자의 판정을 따릅니다. 판정·해결 대상·예산·별은 바꾸지 않았습니다.
- 계획별 최종(대응 완료) 상태:

| 계획 | 판정 | 보조 통로 물·물결 | 깊은 물·표지·충돌 | 정문 |
|---|---|---|---|---|
| 비상전원 + 모래주머니 | 별 1, B 해결 | 없음(젖은 자국) | 없음, 통행 | 깊은 물, 막힘 |
| 비상전원만 | 별 1, B 미해결 | 깊은 물, 물결 | 있음, 막힘 | 깊은 물, 막힘 |
| 비상전원 + 배수펌프(정문만) | 별 2, B 미해결 | 깊은 물, 물결 | 있음, 막힘 | 마름, 통행 |
| 비상전원 + 배수펌프 + 모래주머니 | 별 3, B 해결 | 없음(젖은 자국) | 없음, 통행 | 마름, 통행 |

## 7차: 수첩 넘김 애니메이션·작은 안내 글씨·AI 도움 안내 (2026-11-09, 브랜치 `feature/field-polish`)

### 1. 실제 재생으로 확인한 책 넘김의 어색한 원인
검증 방법: 임시 기록 스크립트(검증 뒤 삭제, 커밋 안 함)로 에디터를 멈추지 않고 실제 속도로 장면을 진행했습니다. 저장은 메모리 저장소만 썼습니다. 매 프레임 화면(640×360)과 프레임 시간을 기록했고, 장면은 다음과 같습니다.
- 현장에서 수첩 펼치기 → 닫기 → 다시 펼치기
- 결과 페이지 넘김
- 다음 현장 넘김 → 닫기
- 시작 연출

수정 전 펼치기·닫기:
- 날아오는 동안 책 전체 투명도가 0.4→1이라, 닫힌 표지 너머로 오른쪽 페이지 글자가 비쳤습니다.
- 표지는 가로 크기만 1→0으로 줄어 '현장 수첩' 글자가 눌렸습니다. 이어서 안쪽 면이 왼쪽으로 펼쳐졌다가 다시 책등 쪽으로 접혀 들어가 **움직임 방향이 한 번 거꾸로** 바뀌었습니다.
- 그사이 왼쪽 페이지가 반투명으로 나타나 뒤쪽 현장이 비쳤습니다.
- 구간마다 따로 선형·가속 곡선을 써서 속도가 끊겼습니다.

수정 전 페이지 넘김:
- 넘어가는 종이가 **내용 없는 빈 줄 노트**라서, 넘김이 시작되는 순간 이전 오른쪽 내용이 사라졌습니다.
- 종이가 책등에 닿는 순간 **왼쪽 새 내용이 먼저 바뀌고**, 그 위로 뒷면이 펼쳐지며 반투명으로 사라졌습니다(잔상).
- 오른쪽 페이지 전체가 회색 사각형 그림자로 어두워졌고, 종이가 ±2° 흔들렸습니다.
- 앞쪽 절반은 가속만 하다가 책등에서 멈추고, 뒤쪽 절반은 감속하며 흐려졌습니다.

수정 전 프레임 멈춤:
- 처음 수첩을 펼칠 때 내용 생성 프레임이 **1.94초** 걸렸습니다(첫 실행의 글꼴·UI 준비). 다음 프레임에 쌓인 시간만큼 날아오는 동작이 한 번에 끝나 버렸습니다.
- 결과·다음 현장 넘김에서는 새 내용을 책등 지점에서 만들어 0.23~0.25초 멈춤이 있었습니다.

### 2. 애니메이션 수정 (`FieldBook.cs`)
- **책등을 축으로 도는 한 장(Leaf)**: 펼친 책과 책등은 그대로 두고 넘어가는 한 장만 움직입니다.
  - 한 장의 피벗은 책등(책 좌표 x=0.5)이고 가로 크기 cos θ, 세로는 1 + 0.018·sin θ(들릴 때만 아주 조금)입니다.
  - 오른쪽 페이지 [0.503, 0.988]과 왼쪽 페이지 [0.012, 0.497]는 책등 기준 거울 위치라서, 뒷면을 자기 가운데 기준으로 한 번 더 뒤집으면 왼쪽에서 글자가 바르게 보입니다.
- **앞뒷면과 내용**:
  - 앞면에는 이전 오른쪽 내용을, 뒷면에는 새 왼쪽 내용을 실제로 옮겨 붙입니다.
  - θ가 90°(폭 0)를 지날 때 앞뒷면을 바꿉니다. 이전 왼쪽 내용은 받침 종이에 남아 있다가 뒷면이 내려앉으며 덮습니다.
  - 새 오른쪽 내용은 넘어가는 장 밑에서 드러납니다.
  - 빈 페이지 깜빡임·잔상 페이드·흔들림은 없앴습니다.
- **표지 열기·닫기도 같은 한 장 방식**입니다.
  - 표지 뒷면에 왼쪽 절반(가죽 + 왼쪽 페이지)이 붙어 함께 넘어오고, 다 펼치면 제자리로 돌아갑니다.
  - 날아오는 동안 책은 불투명합니다. 아래 띠는 페이지가 거의 내려앉은 뒤 나타납니다.
  - 표지(가죽, 0.4초)와 종이 한 장(0.62초)은 그림·길이가 다릅니다.
- **속도 곡선**:
  - 원근이 없는 화면에서는 폭이 cos θ로만 보입니다. 처음에 각도에 곡선을 걸었더니 출발 직후 약 0.3초가 멈춘 듯 보였습니다(기록에서 확인).
  - 그래서 **화면에 보이는 가장자리 위치**에 천천히 출발하고 부드럽게 내려놓는 사인 곡선을 겁니다.
  - 날아오기의 끝 감속과 표지 출발이 이어 붙은 구간도 멈춘 듯 보여서, 두 동작을 겹쳤습니다(날아오기 70%에서 표지 출발, 닫을 때는 표지 80%에서 손 쪽으로 출발).
  - 과한 반동이나 책 전체 흔들림은 없습니다. 정착 동작은 들림(세로 1.018배)과 그림자가 내려앉으며 사라지는 정도입니다.
  - 펼치기는 약 0.57초(이전 0.56초), 닫기는 약 0.46초, 넘김은 0.62초(이전 0.66초)입니다.
- **그림자·두께**:
  - 각도에 따라 면이 조금 어두워집니다(최대 22%).
  - 넘어가는 장 가장자리 바로 바깥에 부드러운 그라데이션 그림자가 생깁니다(너비 최대 책의 7%, 진하기 최대 26%, 들린 만큼만).
  - 페이지 바깥 가장자리에 4px 종이 두께 선을 넣었습니다. 사각형 그림자는 쓰지 않습니다.
- **멈춤 대책**:
  - 새 내용은 넘기기 **시작 전에 한 번만** 만들고, 그 프레임은 움직이지 않은 채 쉰 뒤 넘깁니다.
  - 모든 책 연출의 시간 계산은 한 프레임 0.1초까지만 나아가, 긴 프레임 뒤에도 동작이 한 번에 끝나지 않습니다.
- **소리**: 종이 소리는 표지가 들리기 시작할 때, 페이지는 들리기 시작할 때(가장자리 4% 이동) 한 번만 냅니다. 화면 쪽에서 따로 내던 소리는 없앴습니다.
- **시작 연출**은 같은 `FieldBook.SetCover`로 표지를 넘깁니다. 지도 페이지가 표지 뒷면에 붙어 넘어옵니다.

### 3. 중단·연타 안정성
- 넘김 상태는 `Turn` 하나로 관리합니다. 끝·건너뛰기·다음 넘김 시작·표지 변경 때 `FinishTurn`이 **한 번만** 정리합니다.
  - 새 왼쪽 내용을 제자리로 되돌립니다.
  - 넘기던 장·받침 종이·그림자를 지웁니다.
- 펼침 상태(`SetOpen`)는 위치·회전·크기·투명도·띠 투명도를 정상값으로 맞춥니다.
- 화면 전환은 기존처럼 책 전체를 지웁니다. 수첩 입력 잠금(`notebookBusy`)·확정 중복 방지·결과 버튼 잠금(`ResultReady`)·시작 연출 정책은 그대로입니다.

### 4. 작은 안내 글씨·AI 도움 안내
- 타이틀:
  - 시대 설명을 "2038년 새봄시 · AI 수첩 '내일'과 함께하는 현장"으로 줄였습니다(25, 진한 색, 1366×768에서 약 17px).
  - '이어하기'는 긴 현장 제목 대신 짧은 장소 이름을 씁니다("이어하기 · 현장 2 보건소 (살펴보기)"). 이전에는 자동 축소로 약 11px까지 작아졌습니다.
  - 아래 안내문(창작·비공식)은 진한 바탕 위 23(약 16px)으로 바꿨습니다.
- HUD:
  - 예측 칩은 두 줄까지 23(약 16px)입니다. 이전에는 약 11px였습니다.
  - 문제 이름은 칸을 넓혀 22(약 15px)이고, '추가' 목표는 작은 윗줄로 나눠 이름이 줄어들지 않습니다. 이전에는 약 9~10px였습니다.
- AI 도움(현장 2·3): 'AI 단서' 버튼 왼쪽에 짧은 안내 한 줄을 둡니다.
  - 관찰 전: "관찰을 마치면 AI 단서를 볼 수 있어요"

## 6차: 침수 통행·현장 재도전·수첩 가독성·시작 연출 실측 (2026-11-09, 브랜치 `feature/field-polish`)

### 1. 침수 그림과 통행 범위 일치
- **확인한 문제**: 대피소의 넓은 침수 그림(문제 구역)은 그림일 뿐 통과할 수 있었고, 실제로 막는 것은 길에서 벗어난 작은 웅덩이 두 개뿐이었습니다. 주민은 물 앞에서 기다리는데 플레이어는 같은 진입로 물을 걸어서 지나갔습니다.
- **표현과 판정**: 기존 장애물(`FieldObstacleKind.Puddle`, 사각형 `BoxCollider2D`)을 '깊은 물'로 바꾸어 썼습니다. 새 시스템이나 유체 계산은 없습니다.
  - 얕은 물: 넓은 문제 구역. 옅은 하늘색, 물높이만큼 퍼짐, **늘 통행 가능**.
  - 깊은 물: 진입로·보조 통로의 길 폭 전체를 덮는 사각형. 진한 파랑·뚜렷한 테두리·주의 표지(!)가 **충돌과 같은 사각형·같은 기준(물높이 0.5 초과)**으로 함께 나타나고 사라집니다.
  - 상황 전(초기 징후 0.35·0.12)은 얕은 물, 강우 증가 뒤(물높이 1)는 깊은 물입니다. 배수 뒤에는 깊은 물이 사라지고 젖은 바닥 자국만 옅게 남습니다.
  - 모래주머니는 처음의 얕은 물을 그대로 두고(말리지 않음) 더 들어오지 않게 막습니다. 배수펌프도 강우가 가장 셀 때는 물이 깊었다가 시설이 대응하면서 빠집니다.
  - 문제가 해결되면 그 문제의 깊은 물 그림·충돌만 바뀝니다. 재계획(상황 전)이면 얕은 물·통행 가능으로 돌아갑니다.
- **데이터 이동(대피소)**: 정문 진입로 깊은 물 (0, -2.2) 4.2×3.2, 보조 통로 깊은 물 (10, -1) 3.2×3.2. 정문 주민은 물 남쪽 (1.7, -4.6), 정문 관찰 지점 (0, -4.3), 보조 통로 관찰 지점 (10, 1.5)으로 옮겨 모두 물 밖입니다. 대피 이용객 대기 자리는 큰길의 진입로 입구 (-0.6, -6.0)입니다.
- **갇힘 방지**:
  - 상황이 시작될 때 깊어질 물 안이나 가장자리(몸 반지름 + 0.15)에 서 있으면, 물 사각형 네 변·네 모서리 바깥 후보 중 벽·나무·다른 깊은 물·지도 끝과 겹치지 않는 **가장 가까운 자리로 0.2~0.6초 걸어 나갑니다**. 안전한 자리면 옮기지 않습니다.
  - 건너뛰기·이어하기·엔딩처럼 바로 적용한 상태에서도 막힌 깊은 물과 겹칠 때만 같은 규칙으로 옮깁니다.
  - 대피 이용객은 정문이 확정 판정상 해결되고 **깊은 물이 실제로 빠진 뒤(물높이 0.5 미만)**에만 초당 4.6 걸음으로 진입로를 지납니다. 걸음은 연출이 끝나기 전에 끝나도록 길이를 맞췄습니다(8.1 ÷ 4.6 = 1.75초 < 1.85초).
- **검증기**: 계획 단계(얕은 물)에서 모든 관찰 지점에 걸어갈 수 있는지, 상황 뒤 모든 깊은 물이 막힌 최악의 경우에도 모든 문제를 물 밖에서 살펴볼 수 있는지(재확인·결과 보기·재계획 가능), 깊은 물이 주민·이용객 대기 자리·설치 자리를 덮지 않는지 검사합니다.

### 2. 완주 뒤 현장 선택과 재도전
- **확인한 문제**: 세 현장을 완주한 저장에서는 '엔딩 다시 보기'와 '처음부터 시작'만 있어, 첫 현장만 다시 하려면 진행을 초기화해야 했습니다.
- **화면**: 완주한 저장의 타이틀(엔딩 다시 보기 아래)과 엔딩 최종 화면에 **'현장 선택'**이 생깁니다. 세 카드에 현장 번호·이름·문제 그림·현장 결과 별·최고 기록·'재도전' 버튼이 있고, 아래에 별 합계(현장별 대표 결과로 계산)와 '뒤로 (Esc)'가 있습니다. 좌우 방향키로 카드, 아래로 '뒤로', Enter로 선택합니다. 화면을 떠났다가 오면 마지막에 고르던 카드가 다시 선택됩니다. 진행 초기화는 하지 않습니다.
- **재도전 정책**:
  - 고른 현장만 처음 상태(관찰·계획 없음)로 엽니다. 다른 현장은 다시 시작하지 않습니다.
  - 결과 화면은 **이번 시도의 별·배정** 그대로이고, 버튼은 '같은 현장 다시'·'현장 선택'·'타이틀로'입니다.
  - 대표 결과(완주 기록·엔딩·합계에 쓰는 결과)는 **성공(별 2개 이상)이면서 별이 같거나 많을 때만** 그 시도로 통째로 바꿉니다. 별이 같으면 최신 성공 배정을 씁니다. 실패·하락은 대표 결과·다른 현장·해금·완주를 건드리지 않고, 다른 시도의 배정과 섞지 않습니다(`FieldProgress.SubmitRetry`).
  - 별 합계는 현장별 대표 결과로 다시 계산합니다(누적 없음). 대표 결과가 바뀌면 최고 합계 기록도 더 클 때만 갱신합니다. 현장별 최고 별은 기존처럼 더 많을 때만 갱신합니다.
  - 결과 문구는 "대표 결과가 ★2 → ★3로 바뀌었어요" / "이번 시도 ★3를 이 현장의 대표 결과로 남겼어요" / "이번 시도 ★2 · 대표 결과 ★3가 그대로 남아요" / "이번 시도는 필수 대비가 부족했어요. 대표 결과 ★3와 완주 기록은 그대로예요" 중 하나입니다.
- **저장(버전 1 그대로)**: `retryMission`(재도전 중인 현장 ID), `retryConfirmed`, `retryPicks`(이번 시도 확정 배정), `retryObserved`(이번 시도 관찰)를 더했습니다.
  - 이전 저장에는 이 값이 없고, 빈 문자열·false·빈 목록이 되어 일반 진행으로 읽힙니다.
  - 세 현장을 모두 성공하지 않은 저장이나 엔딩까지 본 단계(Complete)에서는 재도전 정보를 쓰지 않고 경고만 남깁니다.
  - 대표 결과의 배정·관찰(`missions[]`)과 시도의 배정·관찰을 따로 둡니다.
  - 재도전 중 종료하면 그 현장 재도전 맥락(살펴보기: 그 시도의 관찰·편집 계획, 승인 뒤: 그 시도 결과로 상황 후 재확인)으로 이어집니다. 확정했는데 시도 관찰이 모자라면 자동 확정하지 않고 계획으로 낮춥니다. 결과 화면을 보면 시도가 끝나 '엔딩까지 본' 상태로 저장됩니다.

### 3. 수첩 가독성
- **확인한 문제**: 1366×768 실제 Game 뷰(CanvasScaler 1920×1080 기준, 0.5 맞춤 → 약 0.71배)에서 예측 줄·범례·관찰 메모·아래 계획 칸·확정 불가 이유가 자동 축소로 약 8~12px였습니다. M2의 '작은 장치로도 충분' 같은 규칙 단서가 가장 작게 보였습니다.
- **기본 화면에 남긴 것**: 물품 그림·이름·특징·닿는 곳·비용·체크, 고른 자리, 계획 칸(그림 + 자리 이름), 예산·게이지, 승인 버튼과 확정 불가·예산 초과 이유. 핵심 문구는 기준 해상도 23 안팎(1366×768에서 약 16px)이고, 자동 축소 하한은 20~24입니다.
- **관찰 기록**: 이름 + 핵심 단서 한 줄 카드 두 줄 격자. 단서는 미션 데이터의 새 `clue`(16자 이내)이고 긴 문장은 `memo`에 남깁니다. 관찰한 카드를 마우스로 누르거나 방향키로 골라 Enter를 누르면 '자세히' 패널(필수/추가 목표, 필요한 대비, 전체 메모, 주민 말)이 열리고, '닫기'·Esc로 닫으면 그 카드로 선택이 돌아갑니다. 관찰 전 카드는 '아직 못 봄'만 보이고 고를 수 없습니다.
- **말줄임**: 물품의 특징·닿는 곳, 계획 칸 자리 이름은 한 줄로 자르고 넘치면 말줄임표가 붙습니다. 물품 줄을 고르면 지도에 닿는 곳 테두리가 켜지고, 계획 칸을 누르면 그 자리가 선택되어 오른쪽에 전체 이름이 보입니다.
- **AI 도움**: 'AI 단서'는 한 문장 단서 하나(24~30). '배치안까지 보기'는 지점별 물품 목록과 '배치안/지금 계획'의 예산·관찰한 곳 대비 수 비교만 보입니다. 고르는 방식 설명은 '설명' 버튼으로 본문을 바꿔 봅니다. 'AI 단서 → 배치안까지 보기 → 이 계획 적용 → 별도 승인' 흐름과 미관찰 정보 비노출은 그대로입니다.
- **지도**: 범례를 기호 한 줄로 줄였고(확인 전은 지도 안에 '확인 전'), 구역 이름표(20)는 진한 글자 + 종이색 테두리로 어느 바탕에서도 읽히며, 설치 자리 원·이름과 겹치면 아래쪽·가운데·옆 자리로 비킵니다.
- 숨은 패널: 자세히·단서·배치안 패널은 닫을 때 지우며(raycast 남지 않음), 수첩을 닫거나 승인·화면 전환 때 함께 지웁니다. Esc는 자세히 → 단서/배치안 → 수첩 순으로 닫습니다.

## 5차: 저장·주민·AI 도움·시작 연출 정리 (2026-11-07, 브랜치 `feature/field-polish`)

### 1. 빈 재계획 저장·복원 (재현됨 → 수정)
- **원인**: `FieldSave.Restore`가 `draft.Count > 0`일 때만 편집 계획으로 보고, 비어 있으면 재계획 단계에서 이전 확정 배정으로 다시 채웠습니다. JsonUtility는 빈 목록과 없는 목록을 구분하지 못합니다(둘 다 빈 목록). 수정 전 테스트에서 저장 0개 → 복원 2개로 재현했습니다.
- **수정**: 저장에 `draftSaved`(편집 계획을 실제로 저장했는지)를 더했습니다. 값이 true면 빈 계획도 빈 채로 복원합니다. 값이 없는 이전 형식(false)은 편집 데이터 누락으로 보고 이전 동작을 유지합니다(재계획이면 이전 확정 배정을 고칠 수 있게 엶). 버전은 1 그대로이고 하위 호환됩니다. 이전 확정 결과는 진행·비교 정보로 남지만 편집 계획에 다시 채우지 않습니다. 최고 기록·설정 분리는 그대로입니다.

### 2. 대피소 추가 주민 이동 (재현됨 → 수정)
- **원인**: 장식용 이용객이 상황 진행 값(hazard)만 보고 아래쪽에서 목적지까지 곧장 걸었습니다. 대피소 주민은 정문 배수 여부와 관계없이 침수 진입로를 지나갔습니다.
- **수정**: 필요한 이용객에만 `FieldCrowdRoute`(출발·대기 지점·경유점·필요한 문제)를 둡니다. 대피소 주민은 큰길을 따라 와서 진입로 앞 **물 밖 대기 지점**(-3.6, -6.7)에서 기다립니다. **정문 진입로(R)가 확정 판정상 해결되고 시설이 대응한 뒤에만** 진입로 가운데로 올라가 대피소 앞에 섭니다. 전력만 또는 보조 통로만 해결한 계획에서는 대기 지점에 남습니다. 길찾기 시스템은 없고, 대형 펌프 자리와 물웅덩이를 피하는 점 세 개만 잇습니다. 보조 통로 대체 경로는 만들지 않았습니다.
- 정상 재생·건너뛰기·이어하기·엔딩은 같은 최종 상태(`ApplyInstant`)를 쓰고, 재계획(상황 전)이면 다시 숨깁니다. 골목·보건소 이용객은 물을 건너지 않아 그대로 두었습니다.

### 3. AI 도움 단계화
- **첫 번째 도움 'AI 단서'**(수첩 오른쪽 위, 2·3번 현장, 필수 관찰 뒤): `FieldRules.Hint`가 관찰한 문제와 지금 계획을 비교해 **한 가지**만 알려 줍니다. 계획은 바꾸지 않습니다.
  - 순서: 관찰한 필수 문제 중 빠진 대비 → 같은 문제에 효과가 겹침 → 관찰한 곳에 닿지 않는 물품 → 예산 초과 → 관찰한 추가 목표 → "관찰한 곳의 필수 대비가 갖춰졌어요."
  - 예: "관찰한 곳 중 '복도 쉼터'에 마실 물 대비가 빠져 있어요." / "'대기실'에 더위 대비 효과가 겹치고 있어요."
  - 관찰하지 않은 문제는 이름·해결책 어디에도 나오지 않고, 놓을 자리·물품은 알려 주지 않습니다(이미 놓은 자리만 말할 수 있음).
- **추가 도움 '배치안까지 보기'**: 단서 창에서 직접 누를 때만 기존 전체 추천안을 보여 주고, 배치안과 지금 계획의 예산·관찰한 구역 대비를 나란히 비교합니다. '이 계획 적용'을 눌러야 편집 계획이 바뀌고, 적용 뒤에도 직접 고칠 수 있으며 승인은 따로 합니다. 별·진행 불이익은 없습니다. 미션 1은 그대로(도움 버튼 없음)입니다.

### 4. 시작 연출 (약 4.8초)
1. 0~0.9초: 어둠 속 조명이 켜지며 책상 위 닫힌 '현장 수첩'(기존 `FieldBook`)이 드러납니다.
2. 0.9~1.9초: 작은 알림음과 AI '내일' 아이콘, "오늘의 현장 예측이 도착했어요."
3. 1.9~3.0초: 표지가 넘어가며 왼쪽에 새봄시 지도와 빗금 무늬의 예상 위험 아이콘 세 개, 오른쪽에 오늘의 현장 세 곳이 나타납니다.
4. 3.0~4.8초: 수첩이 커지며 흐려지고, 그 아래 타이틀(같은 마을 배경)이 나타납니다.
5. 끝: 제목 '조달 히어로', 부제 '내일을 준비하는 수첩', 메뉴(현장으로 출발 또는 이어하기)가 나타납니다.

- 앱 실행당 한 번만 재생하며(정적 표시, 실행 시작 때 초기화), 타이틀 복귀·새 게임·재계획에서는 다시 나오지 않습니다.
- Space·Enter·Esc·'건너뛰기' 버튼으로 바로 타이틀로 갑니다. 건너뛰기는 저장·새 게임·종료와 연결되지 않습니다.
- 정상 재생과 건너뛰기는 같은 함수(`FinishIntro`)로 끝나고, 메뉴는 **다음 프레임**부터 누를 수 있어 건너뛴 Enter가 '현장으로 출발'을 누르지 않습니다. 연타해도 타이틀은 하나만 만들어집니다.
- 연출 시계는 포커스를 잃으면 멈추고, 한 프레임에 0.1초까지만 나아갑니다. 검증 중 멈췄다 돌아온 첫 프레임에 쌓인 시간만큼 건너뛰는 것을 보고 넣었습니다. `Time.timeScale`과 저장은 건드리지 않습니다. 연출 UI는 끝나면 지워져 메뉴 클릭을 가리지 않습니다.
- 타이틀의 반복 움직임은 수첩 옆 AI 아이콘의 밝기 변화 하나뿐입니다. 버튼은 움직이지 않고, 타이틀을 떠나면 화면과 함께 사라집니다. 공식 로고·승인 표시처럼 보이는 그림은 쓰지 않았습니다.

> 요청서가 말한 '미래 조달 기획서 v3'는 저장소에 없었습니다(`Docs/v2/`까지만 있음). 이번 요청서를 구현 기준으로 삼았습니다.

### 새로 완성한 흐름

출동(AI 예측 카드) → 현장 탐색·관찰(상황 전, 초기 징후) → 수첩 계획(디지털 트윈 지도 · 예상 영향 구역) → **승인** → 배송·설치(물품만 놓임) → **시간 경과**(시계가 지금 → 예측 시각) → **예상 상황 발생** → **시설 자동 대응·주민 이용** → 재확인(걸으며 살펴보기) → 별 평가 → 재계획 또는 다음 현장 → 엔딩.

- 승인 때 배정 목록을 스냅샷(`FieldEvaluation`)으로 고정합니다. 이후 단계는 이 스냅샷만 씁니다.
- 현장 모습은 세 값으로만 정합니다(`FieldWorld`): 그 문제를 계획이 해결하는지(`level`, FieldRules 판정 그대로), 상황 진행(`hazard` 0→1), 시설 대응(`respond` 0→1). 해결된 모습 = `level × respond`. 그래서 설치 중에는 해결 모습·주민 이동·해결 대사가 나오지 않고, 상황이 와야 나타납니다. 연출 안에 별도 성공 규칙은 없습니다. 무작위 요소도 없습니다.
- 새 상태 `FieldState.Scenario`(설치와 재확인 사이). 이 상태에서는 이동·관찰·결과 버튼이 없고 Space·Enter·버튼으로 건너뛰기, Esc로 일시정지만 됩니다. 결과 버튼은 재확인(Review)에서만 생깁니다.
- 정상 재생 끝과 건너뛰기 모두 같은 `ApplyState(result, 1, 1)`을 한 번만 적용합니다(설치 건너뛰기는 `ApplyState(result, 0, 0)`).
- 계획 중에는 시간이 흐르지 않습니다(카운트다운 없음). 일시정지 중에는 상황·시설 대응·시계가 멈춥니다(현장 시간 `FieldDelta`).

### AI 수첩 '내일'과 정보 공개

- 출동 때 예측 아이콘(빗금 무늬 화면 + 상승선)과 예측 한 줄 카드, 현장 HUD 왼쪽 위에 예측 한 줄이 늘 보입니다.
- 수첩 왼쪽 페이지는 '디지털 트윈 지도'입니다. 관찰 전 구역은 빗금·?·"AI 예상 · 확인 전"(문제 종류·해결 예측 숨김), 관찰한 구역은 단색·아이콘·이름·메모(현장 확인). 범례 한 줄을 지도 아래에 둡니다.
- 물품 줄에는 "예상 영향"(관찰한 구역 중 이 자리·물품이 해결하는 곳)을 적고, 줄을 고르거나 마우스를 올리면 지도에 청록 테두리가 켜집니다. 아무 줄도 고르지 않으면 지금 그 자리에 체크한 물품의 영향 구역을 보여 줍니다. 예상 별·정답 목록은 보여 주지 않습니다.
- 확정 버튼은 "계획 승인", 도장은 "승인"으로 바꿨습니다.

### 추천안 비교(보조, 현장 2·3)

- 필수 관찰을 마치면 수첩 오른쪽 위 "추천안 비교"가 켜집니다. 관찰한 필수 문제 해결 수 → 관찰한 추가 목표 해결 수 → 낮은 비용 → 적은 물품 수로 예산 안의 모든 계획을 비교합니다(`FieldRules.Recommend`). 관찰하지 않은 추가 목표는 비교에 넣지 않습니다.
- 추천안은 오른쪽 페이지의 창과 지도 위 반투명 물품 그림으로 보여 주고, "이 계획 적용"을 눌러야 편집 중 계획으로 옮겨집니다. 승인·공급은 하지 않습니다. 창이 열린 동안에는 지점·물품 선택과 승인을 막고 Esc로 닫습니다.
- 예: 보건소에서 H·W만 보면 냉방장치+급수장치(65), O까지 보면 현관 대형 냉방기+급수장치(85).

### field-polish 개선 (2026-11-06, 브랜치 `feature/field-polish`)

바뀐 체험:
- **도착**: 차가 와서 서고 담당자가 내려 둘러본 뒤 말풍선 한 줄("어디가 불편한지 살펴볼까?" / "이번에는 보건소를 확인해 보자." / "비가 오기 전에 서둘러 살펴보자."). 첫 도착 약 4.3초, 이미 본 현장·2번째 현장부터 약 2.6초. Space·Enter·E·클릭·버튼으로 건너뛰기, Esc 일시정지(연출 정지). 재계획에서는 도착 없이 바로 수첩.
- **관찰**: 담당자가 숙여 살핌 → 주민 반응 → 문제 그림이 수첩으로 날아감 → 도착 순간 관찰 수 증가. 반복 관찰은 말풍선만.
- **수첩 지도**: 관찰 전 구역은 빗금과 "? 조사 전"으로 가리고 해결 미리보기를 켜지 않음. 관찰 후에는 문제 그림과 한 줄 메모.
- **수첩 연출**: 손에서 날아와 펼쳐지는 열기(약 0.69초)·닫기, 체크·지우기·흔들림, 예산 숫자·게이지 보간, 확정 도장 → 눌림 → 닫힘 → 배송(약 1.1초), 계획 → 결과와 결과 → 다음 현장 소개에서만 페이지 넘김(약 0.66초).
- **현장**: 깊이 정렬(건물 앞뒤로 지나감), 담당자 숨쉬기·걷기·방향·관찰·수첩 자세, 문제별 주민 동작과 해결 반응, 설치 연출(조명·냉방·급수·전원·배수), 웅덩이는 해결될 때만 그림·충돌 제거.

### 2차 수정 (2026-11-06, 같은 브랜치 `feature/field-polish`)

실제로 고친 것:
- **그늘막과 주민 위치**: 보건소 그늘막 자리를 실제 대기 줄 옆(-3, -3.6)으로 옮기고, 그늘막으로 해결되면 주민이 천막 아래로 걸어가 앉습니다. 현관 대형 냉방기로 해결하면 그늘 대사 없이 현관 바람 앞으로 갑니다. 해결하지 않았으면 원래 자리에 남습니다(`FieldMissionData.reactions`).
- **급수 주민**: 급수장치 옆으로 가서 물을 마시고 빈 물통은 치웁니다. "시원한 물" 표현을 없앴습니다.
- **말풍선·관찰 위치**: 옮겨 간 주민을 따라갑니다(말풍선, 클릭 관찰, 돋보기 안내, 관찰 표시, 다시 살펴보기).

#### 1. 실제 입력 검증

**재현 여부**: 지난 검토의 "시작 버튼 클릭·Enter 무반응"은 **게임 버그로 재현되지 않았습니다.** 원인은 자동 조작 환경이었습니다.
- 이전 검증에 쓴 에디터 키 시뮬레이션(`simulate_key`)은 키보드 장치 상태만 바꾸고 UI 입력 액션(Submit·Navigate)에는 전달되지 않습니다.
- Game 뷰 화면 캡처를 하면 Game 뷰 포커스가 빠지고, 이 프로젝트의 입력 설정(`PointersAndKeyboardsRespectGameViewFocus`)상 포커스가 없으면 키·마우스가 게임에 들어가지 않습니다.

**키 입력 방식에 대한 주의**: 에디터의 키 시뮬레이션(`simulate_key`)은 키보드 장치 상태까지는 바뀌었지만 Game 뷰 포커스 정책 때문에 UI 입력 액션 값이 0으로 남아 화면 조작으로 이어지지 않았습니다. 그래서 InputSystemUIInputModule이 방향키 · Enter를 받았을 때 보내는 것과 같은 uGUI 이동(Move) · 제출(Submit) 이벤트를 EventSystem에 직접 보내 확인했습니다. 실제 물리 키보드로 누른 확인은 아닙니다.

## 8. 확인하지 못한 것과 알려진 제한

- **Windows에서 실행하지 못했습니다.** Mac에서 Windows 빌드 파일만 만들었습니다. Windows PC에서 ZIP을 풀고 처음부터 엔딩까지 플레이해 확인해야 합니다.
- **실제 빌드에서 처음부터 엔딩까지 직접 플레이하지 못했습니다.** 전체 흐름은 Unity Editor 플레이 모드에서 스크립트로 버튼을 눌러 확인했고, 플레이어 빌드는 macOS에서 시작 화면까지만 확인했습니다.
- 사람이 실제 마우스·키보드로 끝까지 플레이한 검증은 아직 없습니다. 키보드 흐름은 uGUI 이동·제출 이벤트로만 확인했습니다(7-1 참고). 실제 키를 눌렀을 때 같은 동작인지는 Game 뷰를 클릭해 포커스를 준 뒤 직접 확인해야 합니다.
- 실패 경로는 가짜 빌드로만 시험했습니다. 실제 Unity 빌드가 실패하는 상황(예: 컴파일 오류)에서 기존 결과가 남는지는 같은 코드 경로를 쓰지만 직접 일으켜 보지는 않았습니다.
- 16:9가 아닌 화면 비율(예: 16:10, 4:3)은 확인하지 않았습니다.
- 소리는 코드로 합성한 간단한 음이며, 실제 스피커 출력은 귀로 확인하지 않았습니다(볼륨 값만 확인).
- Web 빌드는 만들지 않았습니다(WebGL 모듈 미설치).
- Pretendard 파일은 다른 앱에 들어 있던 OFL 파일을 복사했으므로 공식 릴리스로 교체를 권장합니다 (`SOURCES_AND_LICENSES.md`).
- 시연 영상은 촬영하지 않았습니다 (`DEMO_SCRIPT.md`).
- 공모전 규정은 대부분 미확인입니다 (`SUBMISSION_CHECKLIST.md`).
