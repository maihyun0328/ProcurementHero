# ProcurementHero 현장 수첩 버전 제작 프롬프트

아래 지시를 현재 ProcurementHero Unity 프로젝트에서 실행하라.
참고 문서는 ProcurementHero_Game_Design_v2.md다. 첨부되었거나 현재 프로젝트에 있으면 전문을 먼저 읽어라. 다른 프로젝트나 개인 폴더를 찾아다니지 말라. 문서가 없더라도 아래에 적힌 핵심 사양으로 구현을 진행하고, 원문 대조 여부를 보고하라.

## 1 목표와 작업 범위

기존 제품 카드 비교 게임을 현장 탐색과 수첩 체크 중심의 2D 게임으로 개편하라. 기획이나 코드 예시만 제시하지 말고 실제 파일, 씬, UI, 데이터, 연결까지 구현하라.

플레이어는 조달청에서 현장 지원을 나온 담당자다. 마을을 직접 걸어 다니며 문제를 관찰하고, 펼친 수첩에서 설치 장소와 필요한 물품에 체크한다. 계획 확정을 누르면 물품이 배송되고 체크한 위치에 설치된다. 변화한 현장을 다시 확인하고 별 평가를 받는다.

실제 조달청 업무를 그대로 재현하는 것이 아니라 공공구매의 가치를 알리는 가상 체험이다. 제품과 비용, 평가 규칙은 창작이다.

- 먼저 프로젝트 루트, 작업 지침, Unity 버전, 패키지, 기존 코드와 씬, 현재 수정 상태를 확인하라.
- Unity와 URP와 입력 시스템 버전을 임의로 변경하지 말라.
- 기존 수정사항, 에셋, .meta, 라이선스와 저장된 기록을 보존하라.
- 다른 프로젝트 수정, Discard, 강제 푸시, 공개 배포, 자동 제출을 하지 말라. 이 프로젝트의 변경은 아래 Git과 GitHub 작업 규칙에 따라 커밋하고, 연결이 확인된 GitHub 저장소의 작업 브랜치에 푸시하라.
- 사용 가능한 Unity CLI나 에디터 연동 기능을 확인해 활용하라. 도구가 없으면 연동했다고 주장하지 말라.
- 씬과 UI를 직접 생성할 수 없으면 해당 Unity 버전에 맞는 Editor 생성 도구를 만들어 수동 배치를 최소화하라.
- 기존 게임은 남겨 두고 새 플레이용 씬을 분리하라. 새 버전을 실제로 실행 확인한 뒤 시작 씬과 빌드 경로를 연결하라.
- 중요한 동작을 검증한 뒤 다음 단계로 진행하되, 계획서만 작성하거나 첫 미션 골격만 만들고 종료하지 말라.

## 2 핵심 플레이와 화면

타이틀 → 현장 도착 → 탐색과 관찰 → 수첩 계획 → 계획 확정 → 배송과 설치 → 현장 재확인 → 별 평가 → 다음 미션 → 엔딩.

현장은 실제 이동 가능한 탑다운 2D 공간으로 만든다. 캐릭터를 움직이지 않는 기존 비교 화면 위에 수첩 모양만 씌우는 것으로 끝내지 말라.

수첩의 왼쪽 페이지는 현장 지도, 관찰한 문제 그림, 설치 지점이다. 오른쪽 페이지는 현재 지점에 설치 가능한 물품 그림, 짧은 이름, 가격, 체크 칸이다. 아래에는 전체 계획의 작은 그림 목록, 예산 게이지, 계획 확정 버튼을 둔다.

긴 제품 설명, 성능 수치표, 정확한 예상 별점과 정답 판정 문구를 기본 화면에 표시하지 말라. 물품 그림과 현장 변화가 중심이다. 필요한 부가 설명과 출처는 별도 소개 화면에 둔다.

## 3 이동과 관찰

- WASD 또는 방향키로 이동한다. 대각선 이동 속도를 정규화한다.
- 건물, 울타리, 물웅덩이 등의 충돌과 그림을 맞춘다. 필수 관찰 지점은 설치 전에도 모두 접근 가능해야 한다.
- 첫 버전은 주요 장소가 한 화면에 들어오는 고정 카메라로 구성한다.
- 관찰 대상 가까이에 가면 돋보기 아이콘이 나타난다. 클릭, E 또는 Enter로 관찰한다.
- 대상이 겹치면 가장 가까운 유효 대상 하나만 선택한다. 멀리서 클릭했다고 관찰이 완료되면 안 된다.
- 관찰하면 문제 그림이 수첩에 기록되고 대상에 체크 표시가 남는다. 중복 관찰은 기록을 늘리지 않는다.
- 주민 말풍선은 한 번에 하나, 한두 줄로 제한한다. 예: 계단이 잘 안 보여요.
- Tab 또는 수첩 버튼으로 수첩을 열고 닫는다.
- 수첩이 열리면 이동과 현장 연출을 멈춘다. UI와 페이지 연출은 계속 동작해야 한다.
- UI 클릭과 키 입력이 뒤의 현장 관찰이나 이동으로 동시에 전달되지 않게 한다.
- 현장의 Esc는 일시정지, 수첩의 Esc는 계획을 보존하고 수첩 닫기로 처리한다. 한 번 눌러 두 동작이 연속 발생하지 않게 한다.

## 4 수첩 배정 규칙

1. 지도에서 설치 지점을 선택한다.
2. 오른쪽의 물품에 체크하면 해당 지점에 물품 한 개를 배정한다.
3. 다른 물품을 체크하면 교체한다. 같은 물품을 다시 체크하면 취소한다.
4. 지점을 바꾸며 여러 물품을 배정하고 마지막에 계획을 확정한다.

지점당 물품 하나만 배정한다. 같은 물품 종류를 여러 지점에 설치할 수 있으며 지점별로 비용을 합산한다. 수첩을 닫았다 열어도 관찰 기록과 배정 목록과 선택 지점을 유지한다.

계획 중 비용은 예약 비용이다. 항상 현재 배정 목록에서 다시 계산하며 체크 횟수만큼 차감하지 않는다. 예산 초과 계획도 표시하되 경고 아이콘과 붉은 게이지를 보여주고 확정을 차단한다. 해당 지점에서 설치할 수 없는 물품은 선택하지 못하게 한다.

확정 조건은 필수 관찰 완료, 유효한 물품 최소 한 개 배정, 예산 이내다. 일부 문제를 해결하지 못하는 계획도 확정 가능하다. 조건 미충족은 짧은 문구와 아이콘으로 설명한다.

물품을 선택하면 지도에 예상 배치와 효과가 미치는 장소를 강조한다. 미리보기와 실제 해결 판정은 동일한 데이터에서 계산한다. 원 안에 들어왔는데 실제로는 해결되지 않는 식의 모순을 만들지 말라.

## 5 미션 1 밤길을 밝혀라

예산 75. 필수 문제는 A 입구, B 계단, C 안쪽 골목의 어둠이다. D 공원은 추가 목표다. A부터 D는 개발용 ID이며 화면에는 짧은 장소 이름과 그림을 사용한다. 필수 관찰 대상은 A와 B와 C다.

물품은 가로등 35, 보행등 20이다. 각 지점에서 미배정, 가로등, 보행등 중 하나를 선택한다.

설치 지점별 해결 대상:
- 입구 갈림길: 가로등은 A와 B, 보행등은 A.
- 계단 위 갈림길: 가로등은 B와 C, 보행등은 B.
- 공원 가장자리: 가로등과 보행등 모두 D.

예상 효과와 현장 조명은 이 관계에 맞춘다. 해결된 문제 ID의 합집합으로 판정하고 중복 해결을 두 번 세지 않는다. 첫 버전은 원형 거리나 복잡한 광선 계산에 판정을 의존하지 않는다. 문제 구역별 조명이나 어둠 마스크 등으로 지정된 효과를 눈으로 확인하게 하라.

기준 사례:
- 두 갈림길에 가로등 하나씩: 비용 70, A와 B와 C 해결, 별 2개.
- 입구 보행등과 계단 위 가로등과 공원 보행등: 비용 75, A와 B와 C와 D 해결, 별 3개.
- 입구 가로등과 계단 위 보행등: 비용 55, C가 남아 별 1개.
- 세 지점에 가로등: 비용 105, 확정 불가.
- 필수 관찰을 마친 후 공원 보행등만 설치: 비용 20, 필수 해결이 없어 별 0개.

## 6 평가와 재계획

별 3개: 필수 문제 전부와 추가 목표 전부 해결.
별 2개: 필수 문제 전부 해결.
별 1개: 필수 문제 일부 해결.
별 0개: 필수 문제 해결 없음.
성공은 별 2개 이상이다.

확정 시 배정 목록을 결과 스냅샷으로 복사해 고정하고 연타를 막는다. 수첩을 덮고 배송 차량, 상자, 설치 효과를 짧게 보여준다. 건너뛰어도 같은 최종 설치 상태를 한 번만 적용한다.

설치 후 플레이어가 다시 움직이며 결과를 확인하게 한다. 해결된 장소는 밝아지고 주민이 이동하거나 쉬며, 미해결 장소는 불편이 남아야 한다. 성공한 장소가 없어도 관찰 대상 한 곳에서 설치 후 상태를 확인하면 결과로 갈 수 있어야 한다. 별 0개에서 진행이 막히지 않게 하라.

결과는 전후 그림, 도장, 별과 짧은 안내로 보여준다. 성공하면 다음 미션으로 이동 가능하다. 실패하면 재계획을 안내한다. 재계획에서는 현장을 설치 전 상태로 되돌리고 관찰 기록은 보존하며 이전 계획을 수정할 수 있게 한다. 비용과 설치물과 미션 결과는 누적하지 않고 새 확정 결과로 대체한다.

## 7 미션 2와 3

먼저 미션 1을 완주하고 규칙과 조작을 검증한 뒤 나머지 두 미션을 구현하라. 첫 미션에서 멈추지 말고 총 3개 미션과 엔딩을 연결하라.

미션 2 시원한 보건소:
- 더운 대기 공간과 급수 부족을 관찰한다.
- 냉방장치와 급수장치를 설치한다.
- 필수 목표는 대기 공간 냉방과 급수 확보, 추가 목표는 실외 대기 주민의 불편 해소다.

미션 3 비 오기 전 대피소:
- 꺼진 비상등과 물이 고인 진입로를 관찰한다.
- 비상전원과 배수장치를 설치한다.
- 필수 목표는 전력 확보와 필수 진입로 배수, 추가 목표는 보조 통로 확보다.

기획서에서 미확정인 두 미션의 비용과 지점별 효과는 단순하고 검증 가능한 개발 초안으로 직접 정하라. 현장별로 예산을 독립 적용하고 최소 한 개의 성공 조합과 별 3개 조합이 존재하도록 전체 조합을 계산하라. 숫자는 데이터로 분리하고 문서에 개발 초안으로 표시한다. 임의 설정을 사용자가 확정한 사양처럼 쓰지 말라.

세 미션의 별 결과를 보여주는 짧은 엔딩을 만든다. 기존 수치 점수와 새 별점은 같은 저장 키에 섞지 않는다. 기존 사용자 기록을 지우지 말고 새 기록은 버전이 구분된 키에 저장한다.

## 8 표현과 구현 방식

- 플레이어, 길, 건물, 주민, 물품이 구별되는 실제 2D 현장을 구성한다. 가능하면 SpriteRenderer와 Collider2D를 사용하고 수첩과 HUD는 UI로 만든다.
- 임시 도형이라도 담당자 이동, 관찰, 펼친 수첩, 체크, 조명 설치가 모두 눈에 보여야 한다. 설명 문구나 비어 있는 이미지 칸으로 대신하지 말라.
- 수첩은 책등, 좌우 페이지, 체크 칸, 짧은 펼치기 연출을 제공한다. 긴 텍스트 목록 창으로 만들지 말라.
- 기존 한글 폰트와 소리 설정은 상태와 라이선스를 확인해 재사용한다. 한글 누락 글리프와 글자 잘림을 확인한다.
- 물품 그림과 설치 프리팹은 나중에 교체할 수 있게 분리한다. 외부 자산을 사용하면 출처와 라이선스를 기록한다.
- 관찰과 체크와 설치와 도장에 구별되는 짧은 효과음을 제공하고 음소거를 유지한다.
- 아이콘과 색상과 효과음에 짧은 이름이나 상태 표시를 함께 제공한다.
- 키보드 선택이 숨겨진 UI에 남지 않게 한다. 다음 프레임 선택 이동을 쓴다면 닫힌 화면의 UI를 다시 선택하지 않도록 화면 상태를 확인한다.
- 1920×1080과 1366×768에서 현장과 수첩이 잘리지 않게 한다.
- 데이터와 비용 및 해결 판정을 화면 코드에서 분리한다. 불필요한 프레임워크나 패키지는 추가하지 말라.

이동, 관찰, 수첩, 설치, 결과의 입력 허용 상태를 명확히 나누어라. 일시정지와 수첩을 중첩해서 열고 닫아도 이동 잠금이나 Time.timeScale이 잘못 남지 않아야 한다.

기존 미션과 데이터를 삭제해 새 기획으로 덮어쓰지 말라. 재사용할 부분은 재사용하고 새 배정 및 별점 규칙은 별도 데이터와 로직으로 구현한다. 생성 도구를 다시 실행해도 사용자 편집과 에셋을 초기화하지 않게 하라.

제외 범위는 자유 건축, 현장 드래그 배치, 시간 제한, 확률 고장, 온라인 기능, 실시간 AI 대화, 복잡한 배선이다.

- 미션 1의 세 지점별 3가지 상태로 이루어진 27개 조합을 계산한다.
- 위 기준 사례의 비용과 별점과 차단 여부가 맞는지 검사한다.
- 예산과 비용 경계는 별도 계산 테스트로 75 허용과 76 차단을 확인한다.
- 체크 교체와 취소, 미배정과 불가능한 물품, 중복 해결, 확정 스냅샷 독립성을 검사한다.
- 미션 2와 3에 성공 조합과 별 3개 조합이 있는지 검증한다.
- 재계획 결과 교체와 새 저장 키의 기록 갱신을 검사한다.
- 기존 테스트를 무조건 삭제하거나 실패를 숨기지 말고 새 규칙과 기존 규칙의 테스트를 구분한다.

가능한 환경에서 실제 확인:
- 이동과 충돌, 근접 관찰, UI 입력과 현장 입력의 분리.
- 수첩을 여러 번 열고 닫은 뒤 계획과 선택과 잠금 상태.
- 체크, 취소, 확정, 연출 건너뛰기와 일시정지.
- 별 0개부터 3개 결과, 실패 후 재계획, 성공 후 다음 미션.
- 타이틀부터 세 미션과 엔딩까지 완주.
- 키보드만으로 진행, 한글과 두 해상도, Console 오류.

Windows 빌드 모듈이 있으면 새 시작 씬으로 빌드하라. 기존 정상 결과를 먼저 삭제하지 말고 임시 경로에서 빌드와 배포 파일 준비가 성공한 뒤 새 버전 출력으로 정리하라. 실행에 필요한 폴더와 파일을 함께 보존한다. Windows에서 직접 실행하지 않았다면 실행 검증은 미확인으로 보고하라.

## 10 Git과 GitHub 작업 규칙

이 작업은 게임 구현과 함께 Git 커밋 및 GitHub 작업 브랜치 푸시까지 수행하도록 승인된 작업이다. 정상적인 단계별 커밋과 연결된 저장소의 작업 브랜치 푸시는 매번 다시 묻지 말고 진행하라.

### 저장소와 브랜치 확인

- 시작 전에 저장소 최상위 경로, 현재 브랜치, 변경 파일, 스테이징 상태, 원격 저장소와 추적 브랜치를 확인한다.
- 저장소 최상위 경로가 현재 ProcurementHero 프로젝트와 일치하는지 확인한다. 다른 프로젝트나 상위 폴더의 저장소를 잘못 변경하지 않는다.
- Git 저장소가 없고 상위 폴더의 다른 저장소에도 속하지 않으면 현재 프로젝트에서 Git을 초기화한다.
- 기존 저장소에서는 사용자의 현재 HEAD에서 이 작업용 브랜치를 만든다. 예시 이름은 feat/field-notebook-v2이며, 이미 쓰이는 이름이면 충돌하지 않는 이름을 선택한다. 기존 작업 브랜치를 임의로 덮어쓰지 않는다.
- 기존 미커밋 변경과 이미 스테이징된 변경을 먼저 기록하고 보존한다. 깨끗한 상태를 만들겠다는 이유로 reset --hard, clean -fd, checkout -- ., restore ., stash를 자동 실행하지 않는다.
- 원격 저장소는 기존 GitHub 원격 또는 사용자가 지정한 URL을 사용한다. 비슷한 이름의 다른 저장소를 임의로 선택하지 않는다.
- 현재 연결된 원격이 다른 프로젝트이거나 GitHub가 아니라면 임의로 교체하거나 푸시하지 않는다. 로컬 구현과 커밋을 완료하고 필요한 원격 정보를 보고한다.
- GitHub 인증은 기존에 설정된 Git 또는 GitHub CLI 인증을 사용한다. 토큰을 파일, 문서, 로그, 커밋에 남기지 않는다. 전역 Git 설정과 자격 증명을 임의로 바꾸지 않는다.

### Unity 파일 관리

- 첫 커밋 전에 프로젝트 루트의 Unity용 .gitignore를 확인하고 보완한다.
- Library/, Temp/, Logs/, Obj/, obj/, UserSettings/, .vs/와 자동 생성 IDE 파일을 제외한다.
- Builds/, Build/와 배포 ZIP, 캐시, 임시 검증 산출물, 크래시 덤프를 일반 소스 커밋에 넣지 않는다.
- Assets/와 에셋에 대응하는 .meta, Packages/manifest.json과 packages-lock.json, ProjectSettings/, 필요한 기획서와 제작 문서와 테스트는 관리한다.
- 에셋을 추가하거나 이동할 때 .meta와 GUID 연결을 확인한다.
- 이미 추적 중인 파일은 .gitignore만 추가해도 추적이 중지되지 않는다는 점을 확인한다. 자동 생성 파일의 추적을 정리해야 하면 현재 프로젝트의 해당 경로만 git rm --cached로 처리하며 실제 디스크 파일은 보존한다. 기존 관리 정책과 사용자 작성 파일을 먼저 확인한다.
- 새 대형 바이너리가 있으면 GitHub 제한과 저장소의 Git LFS 정책을 확인한다. 실패를 해결하기 위해 기존 이력을 자동으로 재작성하거나 LFS로 일괄 마이그레이션하지 않는다.

### 커밋

- 작업 시작 시점에 있던 사용자 변경을 임의의 백업 커밋으로 묶지 않는다.
- 이후 이번 작업에서 만든 변경만 명시적 파일 경로나 변경 구간을 선택해 스테이징한다. git add . 또는 git add -A로 사용자 변경과 빌드 결과를 한꺼번에 포함하지 않는다.
- 사용자 변경과 이번 수정이 같은 파일에 있으면 diff를 확인해 구분 가능한 변경 구간만 커밋한다. 구분할 수 없는 부분은 보존하고 미커밋 항목으로 정확히 보고한다.
- 커밋 전 git diff --cached로 포함 파일, 의도하지 않은 변경과 비밀정보, 불필요한 바이너리 여부를 확인한다. 기존에 사용자가 스테이징한 변경을 이번 커밋에 섞거나 임의로 해제하지 않는다.
- 빌드와 테스트가 가능한 의미 있는 단계로 나눠 커밋한다. 예: 배정 규칙과 테스트, 현장 이동과 관찰, 수첩과 설치 흐름, 추가 미션과 검증 문서. 단순히 파일 하나당 커밋하지 않는다.
- 커밋 제목은 실제 변경을 설명하고, 필요하면 본문에 수행한 검증과 미확인 항목을 적는다.
- 컴파일 실패 상태를 정상 완료로 커밋하지 않는다. Unity가 없어 확인하지 못한 경우에는 미검증 상태를 숨기지 않는다. 실패를 숨기기 위해 테스트를 제거하지 않는다.
- 커밋 작성자 정보가 없어 막히면 기존 프로젝트 설정을 확인하고, 사용자 이름이나 이메일을 만들어 넣지 않는다.

### GitHub 반영

- 대상 저장소가 확인되고 인증과 권한이 있으면 작업 브랜치를 GitHub에 푸시하고 upstream을 연결한다.
- 푸시 전후 로컬 커밋 SHA와 원격 작업 브랜치 SHA를 비교하여 반영 여부를 확인한다.
- 원격이 앞서 있거나 푸시가 거절되어도 강제 푸시나 자동 이력 재작성으로 덮어쓰지 않는다. 원인을 확인하고 로컬 커밋을 보존한 채 상태를 보고한다.
- GitHub 원격 URL, 권한 또는 인증이 없으면 가능한 게임 구현과 로컬 커밋까지 완료한다. GitHub 반영이 완료됐다고 말하지 말고 필요한 정보나 인증 절차를 구체적으로 알린다.
- 사용자와 저장소 이름이 확인되지 않은 새 GitHub 저장소를 임의로 만들지 않는다. 저장소의 공개 범위도 변경하지 않는다.
- 작업 브랜치의 푸시까지 수행하고 main 또는 master에 직접 푸시하거나 자동 병합하지 않는다. PR 생성은 별도 요청이 있을 때 진행한다.

## 11 완료 조건과 보고

씬 생성기만 작성하고 게임 완성이라고 보고하지 말라. 가능하면 실제 씬 생성, 참조 연결, 컴파일, 플레이, 빌드까지 수행하라. 자동 실행 환경이 없으면 파일 작업을 끝내고 필요한 최소 수동 작업과 미검증 항목을 정확히 적어라.

문서는 실제 실행법과 구현된 규칙과 검증 결과를 중심으로 기존 문서에 필요한 만큼 갱신하라. 새 문서 수나 분량을 늘리는 것보다 게임 완성을 우선한다. 별도 장문의 기획서나 계획만 작성하고 중단하지 말라.

최종 보고에는 다음을 포함하라.
1. 변경한 파일과 새로 실행할 씬의 정확한 경로.
2. 현장 관찰부터 수첩 체크와 설치까지 실제 구현된 기능.
3. 미션 2와 3에서 정한 초안 수치와 성공 조합.
4. 실제 실행한 테스트, 플레이와 빌드 결과.
5. 미확인 항목과 남은 수동 작업.
6. 로컬 저장소 경로, 작업 브랜치, 생성한 커밋 SHA와 제목.
7. GitHub 저장소와 작업 브랜치 링크, 푸시 검증 결과. 푸시하지 못했다면 이유.
8. 남은 미커밋 변경을 기존 사용자 변경과 이번 작업의 미커밋 변경으로 구분한 목록.

게임의 가장 중요한 완료 기준은 사용자가 현장을 걸어 보고, 수첩의 장소와 물품을 체크하고, 확정한 계획에 따라 현장이 바뀌는 과정을 직접 끝까지 플레이할 수 있는 것이다.
